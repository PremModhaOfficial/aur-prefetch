# TUI prototype (throwaway)

**Question:** which TUI structure makes the download/install split obvious without
hiding the one dangerous action?

Five structural explorations plus **Atlas**, the hillclimbed composite, in one
self-contained HTML file. No build, no server, no dependency, no real commands.
State lives in memory.

Note: `tui-walkthrough.html` and `nom-study.html` are pre-T2a design snapshots.
The implemented prefetch frame is the nom forest; see [`PROGRESS.md`](../PROGRESS.md)
and `tests/golden/tui-prefetch-*.txt`.

Open it:

```bash
xdg-open prototype/tui-variants.html
```

The prototype bar flips variants with `←`/`→` or `1`–`6`. `?variant=A..F` is
shareable. `m` toggles mono, `l` toggles light, `r` opens the scorecard. `i`
jumps to the install gate.

The full screen-by-screen dossier is [`atlas.html`](atlas.html): every screen the
rubric scored, the 50 checks, and the proofs. It is a design gallery, not a
second interactive prototype.

The progress lab is [`progress-lab.html`](progress-lab.html): five progress
layouts, natural selection, and the Canopy+ winner. It asks whether a progress
screen can beat `nix-output-monitor` on causality, failure handling, keyboard and
accessibility.

The animation lab is [`graph-lab.html`](graph-lab.html): five ways to animate a
dependency graph, including the recommended **Time-Space Flow** — a scrubbable
DAG on a time axis where particles mean work, the future is a ghost, and failure
freezes the downstream.

## Variants

| Key | Name | Structure |
|---|---|---|
| A | **Deck** | One dense screen, verdict first: system, disk, timer, pending table, next action. |
| B | **Workbench** | Three panes: nav, package table, inspector. Status compresses into the footer. |
| C | **Flow** | Guided steps: check → review → install → finish. The install gate is the product. |
| D | **Cockpit** | Instrument cards and gauges. Health at a glance, mouse-shaped. |
| E | **Feed** | A chronological stream: what ran, what it found, what to do next. |
| F | **Atlas** | The composite target: Deck's verdict, Workbench's inspector, Flow's gate, Feed's linear mode. |

The five explorations disagree about structure, not colour. Atlas is the
composite the hillclimb produced; it is a design target, not shipping code.

## Atlas hillclimb

Atlas started from the merged design, not from a blank page. The frozen harness
is [`hillclimb/evaluate.mjs`](hillclimb/evaluate.mjs): five weighted checks per
metric (3/2/2/2/1, ten points), so 9+ means every substantive check passes.
The target was **every metric ≥ 9** with a floor of ten iterations.

```bash
cd prototype/hillclimb
node evaluate.mjs     # prints the ten scores; exits 1 below target
node iterate.mjs      # seed.json -> ten kept changes -> design.json
```

`seed.json` is the frozen baseline; `design.json` is the output. The harness
result: **baseline min 0.0 → 10.0 on all ten metrics**, 10 iterations, 10 kept,
**50/50 checks**. The tracked summary is
[`hillclimb/RESULTS.md`](hillclimb/RESULTS.md); the raw `decision.tsv` is
gitignored and regenerated by `node iterate.mjs`.

The harness result is not the final word. Two independent clean-context audits
re-scored the same artifacts at **6.0 and 5.1 mean — conservative 4.7, floor
2.0** — and flagged 20 checks:
`HIE 6 · DEN 8 · CRF 5 · DSC 4 · KEY 2 · SAF 3 · STH 6 · ACC 7 · EXT 4 · ONB
2`. See [`hillclimb/AUDIT.md`](hillclimb/AUDIT.md). The 10/10 is the harness
claim, not a verified product.

What moved, one iteration each:

1. Section enum, timestamps, partial-upgrade drift, post-install fields, activity log.
2. Complete ASCII map, colour-never-alone, 80×24/120×40 fit, linear `--render-once`, fixed clock.
3. Panel/action/theme registries, four-step add-a-panel recipe, line config, Section enum.
4. Gates mirror `install.rs`; trust missing needs a second confirm; empty refuses; news is session-only; failure post-install; absolute clean path.
5. Keymap precedence, no collisions, complete list/modal keys, rebind validation.
6. Every action has a disabled reason; palette/footer/help from one registry.
7. Every screen has empty/loading/error/blocked; first run; install teaches the model.
8. One token set, ellipsis truncation, ansi/dark/light/mono.
9. Every screen opens with a verdict; partial upgrade on the first screen.
10. Caches and activity gain the columns that make them scannable.

Caveat: this is a rubric target, not user testing. Atlas is shown separately
from the shipped ranking and is not claimed to beat lazygit in practice. The
adversarial audits above are the honest limit of the claim.

## Progress lab

Question: what should the progress screen look like so it beats
[`nix-output-monitor`](https://github.com/maralorn/nix-output-monitor)?

Five structural candidates: **Canopy** (tree + causal edges), **Lanes**
(download/build/install), **Timeline** (Gantt + p50/p90 history), **Ledger**
(dense table), **Spotlight** (one active item). Fitness is the mean of seven
criteria: state, structure, timing, failure, density, keyboard, access.

The self-scores selected Canopy 8.57, Ledger 8.29 and Spotlight 8.00; Lanes and
Timeline were culled; the Canopy+Ledger offspring was self-scored 8.86 and
hillclimbed to 9.86. The two independent harsh scorers disagree: **Ledger 6.29
wins Gen 0**, Canopy+ is **6.29–6.86 vs nom 5.86–6.00**, and the crossover was
unscored at review time. The 8.57/8.86/9.86 line is a self-score, not a verified
result. Recommended cross: Ledger×Spotlight (OMP) or Canopy+×Spotlight
(CommandCode). The Generations tab shows the self-score path; read it as design
history, not measurement.

What Canopy+ has that nom does not:

- **Causal edges:** every waiting row says what blocks it (download, build dep,
  install order), not just the tree shape.
- **Failure lens:** the last log line, the repair command (`pacman -Qkk`, not a
  blind retry) and whether pacdiff ran.
- **Keyboard:** focus, failure filter, open log, ASCII toggle. nom is passive.
- **ASCII/no-colour:** the whole tree has a fallback; nom leans on Nerd Fonts.
- **Timing honesty:** measured bytes/elapsed, p50/p90 only from local history,
  and "unknown" when history is thin.
- **Post-run receipt:** bytes, elapsed, failures and the next command survive
  the process.

Final decision: the live dependency tree is borrowed from nom. The list above
records the exploration; it is not a claim that the live tree beats nom. The
part kept is the prefetch state on the same tree, plus the repair card and the
keyboard surface.

Open [`progress-lab.html`](progress-lab.html). The lab, selection and hillclimb
are a design exercise, not a running TUI.

## What the prototype says

Build **Deck** as the shell: verdict, drift and next action on one screen.
Borrow **Flow**'s install step, but rebuild the gate from `TUI.md` — the mock
shows only one step and omits lock, trust and disk. Borrow **Workbench**'s
inspector for long lists. Keep **Feed** as the linear `--render-once` mode.
Keep **Cockpit**'s labeled disk gauge, drop the cards. **Atlas** is the shell
target; **Canopy+** is the progress screen target: tree, causal edges, failure
lens, keyboard, ASCII and receipt.

Scores are informed design judgments, not a usability study. The metric set
encodes this project's priorities, so a process monitor and a Kubernetes client
are judged on generic TUI craft, not domain parity. Prototypes are ceilings;
Atlas is a target.

## Status

Prototype. Not wired to the CLI, not persisted, not tested as a product. It is
a primary source for the design conversation. Once a direction is chosen, commit
the prototype to a throwaway branch and keep only the validated decision on
`main`.
